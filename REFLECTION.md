# Reflection

I drew the lines between the tools by side effects and by who owns the decision. `get_weather_forecast` (Data) is a pure read and knows nothing about what a "good" day is, so it stays reusable. `save_reminder` (Action) is the only tool that writes, and it only validates and stores. `plan_outing` (Orchestration) owns the policy: the rain and temperature thresholds, whether anything gets saved, and what to suggest instead. I considered a separate geocoding tool, but the model never needs coordinates, so I kept geocoding as an implementation detail of the forecast tool. That leaves a small "and" hidden in its description (resolve the city, then fetch the forecast), which I accepted on purpose. I also put the real logic in a plain `core.py` that the orchestrator calls directly rather than re-entering MCP. That made the tools easy to unit test, but it means the inner calls don't exercise the protocol. Raising `ToolError` for bad input or an unavailable service means the model receives a readable message and can correct itself or tell the user, instead of failing silently.

Three tools felt right for a demo and for the assignment's constraint, but tight for a real product. I would add a `list_reminders` and a `delete_reminder` tool (right now reminders are readable only through an MCP resource, which my client does not hand to the model) and make `save_reminder` idempotent so repeated requests don't create duplicates. Next steps: write a small set of routing test prompts to measure how often the agent picks the right tool, move from stdio to Streamable HTTP so the server can run separately from the client, and replace the local database with a real calendar integration.
